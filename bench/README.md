# Benchmark: SQL vs. Python on the same data

Four analytical workloads, each defined twice — once as SQL for `zarr-cli`, once
as xarray for Python — computing the same result over the same store. The driver
runs both and prints a comparison.

```bash
cargo build --release --bin zarr-cli      # the SQL side needs a release build
uv run bench/run_bench.py                 # all four workloads, 3 reps each

uv run bench/run_bench.py --only q4_ndvi  # one workload
uv run bench/run_bench.py --reps 5        # more repetitions
uv run bench/run_bench.py --engine python # one side only
```

Results land in `bench/out/` — a `results.json` with every run, plus a per-run
log for each engine so a failure can be read rather than guessed at.

## Results — 2026-07-20

**Environment.** GCE `e2-standard-8` (8 vCPU, 31 GB), zone `us-central1-b`,
Debian 13, Rust 1.97.1 release build. `q1`–`q3` read public ARCO-ERA5
(`gs://gcp-public-data-arco-era5/ar/full_37-1h-0p25deg-chunk-1.zarr-v3`) from the
same region; `q4` reads a local 6.47 MB store on `pd-standard`. Three repetitions
per engine, each a fresh process. Python is xarray 2026.4.0 / zarr 3.2.1.

### Steady state — query execution, store already open

The comparison for a notebook or service, where opening is paid once and
amortized. `warm` is the mean of reps 2–3.

| Workload | SQL | Python | Result | Bytes read |
|---|---|---|---|---|
| `q1_nino34` — Niño-3.4 box mean | **0.989 s** | 25.824 s | **SQL 26.1×** | 32.64 MB |
| `q2_diurnal` — diurnal climatology | **1.208 s** | 27.374 s | **SQL 22.7×** | 166.78 MB |
| `q3_point` — point timeseries | **2.342 s** | 7.343 s | **SQL 3.1×** | 1.73 GB |
| `q4_ndvi` — NDVI per pixel | 0.186 s | **0.070 s** | **Python 2.7×** | 6.49 MB |

### Cold start — open the store and run the query once

What a script, cron job or dashboard actually pays. SQL's `open` is
`CREATE EXTERNAL TABLE` (schema inference); Python's is `open_zarr`.

| Workload | SQL open | SQL query | **SQL total** | Py open | Py query | **Py total** | Result |
|---|---|---|---|---|---|---|---|
| `q1_nino34` | 0.413 s | 0.989 s | **1.402 s** | 1.402 s | 25.824 s | 27.226 s | SQL **19.4×** |
| `q2_diurnal` | 0.218 s | 1.208 s | **1.426 s** | 1.441 s | 27.374 s | 28.815 s | SQL **20.2×** |
| `q3_point` | 0.240 s | 2.342 s | **2.583 s** | 1.192 s | 7.343 s | 8.535 s | SQL **3.3×** |
| `q4_ndvi` | 0.003 s | 0.186 s | **0.190 s** | 0.287 s | 0.070 s | 0.357 s | SQL **1.9×** |

Row counts agreed between engines on all four workloads. Where values were
checked, `q1` gave 28.652078 (SQL) against 28.652084 (Python) — a 6×10⁻⁶ gap
consistent with float32 accumulation order, not a discrepancy.

### How to read this

**We lose `q4_ndvi`, by 2.7×.** Pure per-pixel arithmetic on a small local store
is numpy's home ground, and no amount of I/O work changes that: an earlier fix cut
this workload's reads 16× (103.57 MB → 6.49 MB) and the wall clock did not improve,
because I/O was never the bottleneck here. It is Arrow batch construction against a
vectorised numpy expression. It stays in the table.

**`q3_point` is the least trustworthy number.** It moves 1.73 GB per repetition —
by far the most of any workload — and repeated runs have shown a 2.6× spread on
identical work with byte-identical reads, i.e. network throughput variance rather
than anything in the engine. Treat its 3.1× as indicative and rerun with 7–9 reps
and a median before quoting it.

**None of this predicts another workload.** These numbers illustrate a cost model
on one archive, one machine, one day.

### A note on when these were measured

An earlier run of this same suite reported materially worse SQL numbers — `q2` at
4.5 s rather than 1.2 s — because the scan was re-reading chunks up to 37× under
its default configuration. The benchmark was measuring our own bug. Byte counts
are the tell: `q2` fell from 500.33 MB to 166.78 MB with no change to the query.

The lesson is procedural: **rerun the suite after any change to the read path, not
only before publishing**, and watch `bytes read` as closely as the wall clock. A
timing regression can hide in noise; a 3× change in bytes fetched cannot.

## The workloads

Each was chosen for a different *shape* of work, not as a variation on one theme.
Three read public ARCO-ERA5 over GCS and need no local data; the fourth is local.

| | Workload | Shape it tests | Data |
|---|---|---|---|
| `q1_nino34` | Niño-3.4 box mean SST, 24 h | narrow, highly selective filter | ARCO-ERA5 (GCS) |
| `q2_diurnal` | diurnal climatology, CONUS, 3 days | grouped aggregation → 535,704 rows | ARCO-ERA5 (GCS) |
| `q3_point` | one grid cell × 744 hourly steps | needle-in-a-haystack — **our weak case** | ARCO-ERA5 (GCS) |
| `q4_ndvi` | NDVI per pixel, 1024² scene | pure projection, no reduction | local Zarr |

`q4_ndvi` needs `data/s2_ndvi_scene.zarr`, which is ~6 MB and is generated by
`uv run scripts/gen_ndvi_scene.py`. The driver skips the workload with a warning
rather than failing if it's absent.

## Why q3 and q4 are in here on purpose

Both were included expecting them to be unflattering, on the principle that a page
with four green checkmarks invites a technical reader to assume cherry-picking. One
of them behaved as predicted; the other didn't, and both are worth keeping.

**`q3_point` — the chunk-layout case.** ARCO-ERA5 stores one timestep per chunk
spanning the whole lat×lon plane, so a single grid cell across 744 hours means
fetching 744 chunks of roughly 4 MB and discarding all but one cell of each. The
1.73 GB in the results table is that cost, and it is irreducible for *any* reader
of this store — it is a property of how the data was written, not of the engine.
xarray fetches the same 1.73 GB, which is why we still come out 3.1× ahead rather
than behind. The honest conclusion is about layout: point lookups over a time-major
archive want rechunking or a materialised extract, and a columnar copy would beat
both engines here by a wide margin.

**`q4_ndvi` — the case we lose.** Per-pixel arithmetic over a small local store is
numpy's home ground and we are 2.7× slower. Worth stating plainly, because it also
bounds the claim: our advantage is in selective reads and grouped aggregation over
large chunked archives, not in raw array arithmetic.

## What is measured, and what isn't

**Two clocks.** `engine` is what the engine reports for executing the query;
`wall` is the whole process as timed by the driver, including startup. Python's
scientific stack takes a second or more just to import, and charging that to
query performance would misrepresent it — so both are recorded and the comparison
uses `engine`.

**Cold and warm are separate.** Every repetition is a fresh process. The first is
labelled `cold`, the rest `warm`, and they are never averaged together. Blending
them is the most common way a benchmark quietly flatters itself.

**Output is never rendered.** Both engines stop their clock once the result is
materialized in memory, and stdout is redirected to a log. Printing half a million
rows to a terminal measures the terminal.

**Row counts are cross-checked.** After each workload the driver compares the row
count the SQL CLI reports against the one the Python script reports. A mismatch is
printed as `MISMATCH` in the summary, because two timings for two different
computations are worse than no timings at all.

**`bytes read` is honest about not knowing.** The SQL side reports what the engine
actually fetched. xarray exposes no comparable counter, and some Zarr paths
(icechunk, VirtualiZarr) do their own object I/O — all of these report `n/a`,
never `0`. Zero would read as a measurement showing no I/O.

**Everything runs at stock settings.** No `ZARR_MEM_BUDGET_BYTES`, no tuned
`batch_size` — the scan uses its built-in 256 MiB read-window ceiling, divided by
the partition count. This matters for reproduction: the ceiling determines whether
the read window can cover a whole chunk row, and therefore whether chunks are read
once or many times. Setting it *lower* than the default can reintroduce large read
amplification on stores with big chunks; the scan warns when that happens rather
than paying it silently.

## Making the Python side a fair opponent

The baseline has to be the code a competent user would actually write, or the
comparison is worthless — their team will rewrite it in five minutes and beat it.
Specifically:

- Stores are opened lazily with `chunks={}` so dask fetches only the selection.
  Eagerly loading the cube and slicing afterwards would be a strawman.
- **ARCO-ERA5 is opened with `drop_variables`.** This one is worth its own note,
  because getting it wrong inflated our published numbers once already. A plain
  `xr.open_zarr()` acquires metadata for all 273 data variables before returning
  — measured at ~97 s from a home connection and ~49 s in-region, *regardless of
  which single variable you then query*. Dropping the untouched variables cuts it
  by roughly 16x (96.9 s → 5.9 s locally) and loses nothing: label-based `.sel()`
  still works and the answer is identical. Two neighbouring ideas were measured
  and rejected — `decode_times=False` saves nothing at all (95.7 s vs 96.9 s, so
  the cost is per-variable metadata rather than CF decoding), and dropping to raw
  `zarr.open_group` is fastest (1.07 s) but gives up label selection, which is the
  very thing the SQL `WHERE` clause is being compared against.
- Coordinate ranges are selected by boolean mask, not `slice`. ERA5's latitude
  axis descends, so `slice(-5, 5)` silently returns nothing — a trap the SQL side
  doesn't have, and one that would hand us a fake win.
- Reductions pass `skipna=False` to match DataFusion's `AVG`, which propagates
  NaN rather than skipping it. Left at the default the two engines quietly compute
  different things over any variable with masked cells.
- Rounding is matched to the SQL (`ROUND(..., 3)` in q2, `ROUND(..., 4)` in q4) so
  the fingerprints are comparable rather than differing in the last decimal.

One asymmetry worth stating rather than hiding: `q4_ndvi`'s SQL says
`ORDER BY y, x`, while the Python gets that ordering for free by transposing a
grid it already holds. That is a real advantage of the array layout, not a step
the Python skipped — but it means the two sides are not doing identical work for
that clause.

## Known gaps

- **Metadata reads aren't counted** in `bytes read`. Schema inference runs when
  the table is registered, against an untracked store, so the first query's
  metadata cost is real but invisible.
- **There is no third column yet** for the materialise-then-query path (convert to
  Parquet, query with DuckDB). That is the comparison that speaks most directly to
  a pipeline which already materialises, because its total cost includes the
  conversion job.
- **These numbers don't predict anyone else's workload.** They illustrate a cost
  model on one archive and one machine.
